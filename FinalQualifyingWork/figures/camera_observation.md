# CameraObservation — пояснение к блок-схеме `camera_observation.drawio`

Документ описывает, **как по изображению с курсовой камеры получают оценку положения БВС** в локальной системе координат трассы и сохраняют её как `CameraObservation`.

Порядок совпадает с блок-схемой (§ **3.5** ВКР).  
Код offline-конвейера: `tools/exp11_camera_module_import/generate_camera_observations.py`.  
Схема данных: `dct/camera_localization/observation.py`.

---

## Главная идея (одним абзацем)

На трассе **заранее известны** координаты ворот в 3D. Нейросеть **YOLO** на кадре видео находит ворота и четыре **внутренних угла** в пикселях. Задача **PnP** (Perspective-n-Point) отвечает на вопрос: *«где должна стоять камера (дрон), чтобы эти 3D-точки спроецировались именно в такие 2D-точки?»* Ответ — `xyz_obs`. Чтобы не перепутать похожие ворота, используется **грубая позиция** из телеметрии (coarse prior) и перебор гипотез **Top-K**.

---

## Что такое CameraObservation

Это **одна запись** «камера в момент времени t считает, что дрон здесь»:

| Поле | Смысл |
|------|--------|
| `timestamp` | Время на общей шкале `ts_wall` |
| `xyz_obs` | Позиция в координатах трассы (x, y, z), метры |
| `sigma_cam` | Оценка погрешности наблюдения, метры (в коде — `q_out_m`) |
| `confidence` | Уверенность выбранной гипотезы ворот |
| `gate_id` | Какие ворота сопоставлены детекциям |
| `reprojection_error_px` | Насколько хорошо 3D→2D совпали (RMSE в пикселях) |
| `status` | `ok` — можно подавать в PF; `rejected` — отброшено |
| `bbox_xyxy`, `keypoints` | Для отрисовки в Replay |

В PF попадают только записи с `status == "ok"` и `sigma_cam > 0` (см. `inject_ready`).

---

## Вход: кадр и время

**Источник:** `video.mp4` из папки сессии DCT.

**Время кадра:** из `video_timestamps.parquet` (столбец `ts_wall` по `frame_idx`).  
Без этого нельзя сопоставить кадр с телеметрией и RC.

**Сэмплирование:** в скрипте по умолчанию обрабатывается каждый 6-й кадр (`--every-n-frames 6`), чтобы ускорить offline-прогон.

## Условие: есть coarse prior?

**Вопрос на схеме:** есть ли в `telemetry.parquet` позиция `pos_x, pos_y, pos_z` около времени кадра?

| Ответ | Действие |
|-------|----------|
| **Нет** | Кадр **пропускается** (без prior нельзя сузить список ворот) |
| **Да** | Берётся ближайшая по времени строка телеметрии |

### Coarse prior — простым языком

Это **приблизительное** «где мы на трассе сейчас», не от камеры, а от другого источника:

- в симуляторе — ground truth или выход PF/KF из `telemetry.parquet`;
- в перспективе online — оценка `OnlineLocalizer` / `KFLayer2`.

Обозначим грубую позицию **p_coarse** = (x, y, z).  
Параметр **q_m** (`prior_q_m`, по умолчанию ~5 м) — насколько мы **не уверены** в prior: от него зависят радиусы поиска ворот-кандидатов.

**Зачем prior:** на кадре может быть несколько ворот, а YOLO не пишет номер ворота — только «прямоугольник и углы». Prior говорит: «ищи ворота **рядом** с этой точкой», а не по всей трассе.

## 1. YOLO — что видим на изображении

**Вход:** кадр BGR (цветное изображение).

**Выход модели** (класс `gate`, pose/keypoints):

- **bbox** — рамка ворот на экране;
- **4 keypoints** — внутренние углы ворот в **пикселях** (u, v).

**Фильтрация** (`YoloAdapterConfig`):

- минимальная уверенность keypoints (`min_keypoint_confidence`, напр. 0.7);
- минимальная площадь bbox;
- не больше `max_detections` лучших детекций.

### Условие: есть валидные детекции?

| Ответ | Действие |
|-------|----------|
| **Нет** | `CameraObservation` с `status=rejected` (нет ворот в кадре или плохое качество) |
| **Да** | Переход к привязке ворот и PnP |

**Простыми словами:** YOLO отвечает только на вопрос *«где на картинке углы?»*, но **не** на вопрос *«это ворота №3 или №7?»*.

---

## 2. Кандидаты gate_id (CoarseRefine)

**Вход:** список детекций + `p_coarse` + `q_m`.

**Карта трассы** (`track.json` / `GateMap`): для каждого ворота с известным `gate_id` хранятся **3D-координаты четырёх углов** в мировой (трассовой) системе.

**Кольца поиска** вокруг prior на горизонтальной плоскости (X, Z):

- **near** — близко к prior (радиус порядка q_m);
- **mid**, **far** — шире;
- **extra** — остальные ворота трассы (хвост списка).

Для **каждой** детекции YOLO формируется список **допустимых** `gate_id` (обычно до ~14), отсортированных по расстоянию до prior.

**Аналогия:** вы знаете, что вы где-то на 3-м повороте трассы (prior). На фото — два ворота без номеров. Вы рассматриваете только ворота 2, 3, 4, 5, а не все 20 на трассе.

## 3. Top-K + PnP — как получаем xyz_obs

Это центральный блок: **связать картинку с 3D-миром**.

### Шаг A — гипотезы «какое ворото где»

`TopKHypothesisGenerator` перебирает комбинации:  
детекция 1 → gate_id a, детекция 2 → gate_id b, …  
(с ограничением по кандидатам и бюджету времени ~200 ms).

Для каждой комбинации вызывается **PnP**.

### Шаг B — математика PnP простым языком

**Дано:**

- 3D-точки углов ворот на трассе: **P_j** (метры, система трассы);
- 2D-точки на изображении от YOLO: **p_j** (пиксели);
- матрица камеры **K** (фокус, центр, дисторсия) из `camera_calibration.json`.

**Ищем:** положение и ориентацию камеры (позу), чтобы при проекции

```
пиксель p_j  ≈  проекция(K, поза, P_j)
```

ошибка была минимальной.

**В коде** (`PnPSolver`):

- для одного ворота — несколько кандидатов позы (разные порядки углов IDENT/HFLIP, зеркальная неоднозначность);
- для нескольких ворот — совместный PnP по всем углам;
- отсекаются нереалистичные позы (камера «сзади» ворот, слишком низко);
- побеждает гипотеза с **наименьшей ошибкой репроекции** (RMSE в пикселях).

**Результат PnP:** `position_world` — трёхмерная точка, принимаемая за положение камеры/БВС → это и есть **`xyz_obs`**.

**Аналогия:** вы стоите в комнате и видите угол стола. Зная размер стола и положение углов в комнате, можно вычислить, **где вы стоите**, чтобы угол на вашей фотографии попал именно туда. Ворота — «известный стол», YOLO — «где угол на фото».

### Шаг C — выбор лучшей гипотезы

`CoarseRefineLocalizer` выбирает гипотезу, у которой:

- PnP успешен;
- поза **ближе** к `p_coarse` (в горизонтальной плоскости);
- низкая ошибка репроекции и разумный разброс между кандидатами.

Считается **`q_out_m`** — итоговая неопределённость наблюдения (станет `sigma_cam`).

### Условие: refine.success и q_out допустим?

Отклонение (`status=rejected`), если например:

- нет ни одной гипотезы Top-K;
- визуальная поза **слишком далеко** от coarse prior;
- наблюдение «бесполезно» (почти не улучшает prior);
- `q_out_m` выше порога внедрения (`q_injection_max_m`).

| Ответ | Результат |
|-------|-----------|
| **Да** | `CameraObservation`, `status=ok` |
| **Нет** | `status=rejected`, `reason=...` |

---

## 4. CameraObservation (ok) и запись

При успехе:

```
xyz_obs = position_world из PnP
sigma_cam = q_out_m
confidence, gate_id, reprojection_error_px — из выбранной гипотезы
```

Все наблюдения кадра пишутся в **`camera_observations.jsonl`** (одна строка JSON на кадр).

## Далее: слияние с PF (§ 3.6)

`CameraObservation` **не заменяет** RC-локализацию. В Replay/online вызывается:

```
inject_position_observation(xyz_obs, sigma_cam)
```

Для каждой частицы PF: 3D-позиция на референсе сравнивается с `xyz_obs`, веса умножаются на

```
exp( −½ · ||xyz_частицы − xyz_obs||² / sigma_cam² )
```

затем ESS/ресемплинг и circular mean — как в [`pf_cycle.md`](pf_cycle.md), но **без шага predict**.

**Простыми словами:** камера иногда говорит «ты не там, где думал PF» — и голоса частиц пересчитываются.

---

## Два источника неопределённости (важно для текста ВКР)

| Источник | Что ограничивает |
|----------|------------------|
| **YOLO + PnP** | Видны ли ворота, калибровка, ошибка репроекции → `reprojection_error_px`, отбор гипотез |
| **Coarse prior** | Какие `gate_id` вообще рассматриваются |
| **q_out_m → sigma_cam** | Насколько сильно PF доверяет этому кадру |

Плохой кадр лучше **отклонить** (`rejected`), чем сломать PF большим весом.

## Один кадр целиком (цепочка)

1. Кадр + `ts_wall`  
2. `p_coarse` из telemetry (иначе skip)  
3. YOLO → keypoints в пикселях  
4. Кандидаты `gate_id` вокруг prior  
5. Top-K + PnP → `position_world`  
6. Проверки → `ok` / `rejected`  
7. Строка в `camera_observations.jsonl`  
8. (позже) inject в Particle Filter
