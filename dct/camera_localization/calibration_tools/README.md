# Модуль: calibration

## За что отвечает

Оценивает внутренние параметры камеры (матрицу K и коэффициенты дисторсии) по известным 2D–3D соответствиям точек ворот из аннотированных кадров Liftoff-симулятора.

**Входные данные:**
- `calibration/calibration_frames_card.json` — 12 размеченных кадров:
  - 6 кадров-кропов с одним воротом (`fov_frames`) — для FOV-калибровки
  - 6 полных кадров с несколькими воротами (`multi_frames`) — для уточнения

**Выходные данные:**
- `config/camera_calibration.json` — матрица K, коэффициенты дисторсии, RMS ошибка репроекции

---

## Система координат

Используется мировая система координат Liftoff:
- **Y-up**: ось Y направлена вверх
- `position` в карте ворот = нижняя центральная точка ворот (bottom center)
- Порядок углов ворот в **модели трека** (иконический): `inner_top_left → inner_top_right → inner_bottom_right → inner_bottom_left`

---

## Разметка ключевых точек в JSON

Для каждого ворота в `calibration_frames_card.json` у ключевых точек заданы те же имена (`inner_top_left`, …). В симуляторе аннотация задаётся **со стороны наблюдателя на кадре**. В большинстве кадров это совпадает с порядком модели (`TL → TR → BR → BL` как в треке). В части кадров порядок оказывается **горизонтально зеркальным**: визуальный «верхний левый» на изображении соответствует **3D inner_top_right**, и т.д. — перестановка `(1, 0, 3, 2)` относительно поля `keypoints` в JSON (**HFLIP**).

Скрипт калибровки сопоставляет 3D-углы из `gate_model` с точками в JSON **в том порядке, в каком они записаны** — поэтому при несоответствии реального порядка иконическому именованию вырастает ошибка репроекции. Подробнее об учёте двух вариантов порядка при оценке позы камеры см. модуль [`pnp_solver`](../pnp_solver/README.md).

### Planar PnP и последующая локализация

Четыре угла одной рамы лежат **в одной плоскости**. Для задачи вида «по одной раме оценить позу камеры» (PnP) это даёт **две** математически согласованные позы при малых ошибках в пикселях: координаты ворот в мире заданы треком, а **положение камеры** при одной и той же проекции может соответствовать двум симметричным вариантам. Калибровка внутренних параметров по многим кадрам и воротам этой неоднозначности не снимает — она проявляется уже при **валидации позы** и в рантайме. Имеет смысл закладывать в пайплайн дополнительные ограничения (несколько ворот, фильтр по времени, IMU и т.д.); обоснование и эвристики выбора кандидата описаны в [`pnp_solver/README.md`](../pnp_solver/README.md).

## Допущения для симулятора

Liftoff использует виртуальную камеру без оптических искажений:
- **Нет дисторсии** — все коэффициенты фиксированы в 0 по умолчанию
- **Квадратные пиксели** — `fx = fy` (флаг `CALIB_FIX_ASPECT_RATIO`)
- Флаг `--allow-distortion` позволяет оценить K1, если нужно проверить

---

## Запуск

```bash
# Из корня репозитория
python src/calibration/calibrate_camera.py

# С оценкой дисторсии (опционально)
python src/calibration/calibrate_camera.py --allow-distortion

# Кастомные пути
python src/calibration/calibrate_camera.py \
    --calib-json calibration/calibration_frames_card.json \
    --output config/camera_calibration.json
```

---

## Формат выходного файла

```json
{
  "camera_matrix": [[fx, 0, cx], [0, fy, cy], [0, 0, 1]],
  "dist_coeffs": [k1, k2, p1, p2, k3],
  "image_size": [1280, 720],
  "reprojection_error_px": 1.23,
  "calibration_frames": ["frame_000107_gate_0.jpg", ...],
  "n_point_correspondences": 44
}
```

## Качество калибровки

| Метрика | Ожидаемый диапазон |
|---|---|
| Общий RMS (все кадры) | < 5 px (симулятор, мало кадров) |
| RMS на лучших кадрах | < 2 px |

Если RMS > 10 px — проверить порядок соответствий 2D–3D (в том числе возможный **HFLIP** разметки, см. раздел выше).
