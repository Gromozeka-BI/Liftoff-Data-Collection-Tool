# Модуль: pnp_solver

## За что отвечает

Принимает **2D-детекции углов ворот** (результат работы детектора или ручной разметки) и **карту трека**, после чего:

1. Находит 3D-мировые координаты соответствующих углов через `gate_model`
2. Генерирует возможные PnP-позы камеры по каждому видимому гейту
3. Устраняет/сужает **зеркальную неоднозначность** planar PnP через multi-gate consensus
4. Возвращает выбранную позу камеры/дрона: `(x, y, z)` + `yaw_deg`

gate_detections = [

```python
PnPResult(

    n_points=4,                            # использовано соответствий
    gate_ids=[0],                          # какие ворота участвовали
    perm_used="HFLIP:c1"                   # выбранные перестановки/кандидаты
)
```

## Алгоритм

### Режим одних ворот (4 компланарные точки)

1. Берём 3D-углы ворот из `gate_model` в фиксированном порядке `TL→TR→BR→BL`.
2. Пробуем две рабочие трактовки порядка 2D-точек:
   - `IDENT = (0, 1, 2, 3)`
   - `HFLIP = (1, 0, 3, 2)`
3. Для каждой трактовки запускаем `cv2.solvePnPGeneric(SOLVEPNP_IPPE)` → до двух зеркальных кандидатов.
4. Для одиночного гейта выбираем физически допустимый кандидат по стороне гейта, высоте и RMSE.

Важно: четыре угла одного гейта лежат в одной плоскости, поэтому **минимальный RMSE не гарантирует правильную позу камеры**. Планарный PnP может дать зеркальную позу с отличной репроекцией.

### Режим нескольких ворот (≥ 2 ворот)

1. Для каждого гейта строим single-gate кандидатов `IDENT/HFLIP × IPPE(c0/c1)`.
2. Для каждого кандидата получаем независимую оценку положения камеры.
3. Выбираем **consensus-кластер** по независимым позициям камеры:
   - кандидаты разных ворот должны давать близкие позиции камеры;
   - RMSE используется как вторичный критерий, а не главный;
   - для ворот, лежащих на одной линии/плоскости, дополнительно выводится общая сторона камеры по порядку центров ворот на изображении;
   - Y-фильтр в multi-gate мягкий: правильный XZ-кандидат иногда имеет зеркальную высоту.
4. После выбора consensus можно запускать joint refine (`SOLVEPNP_ITERATIVE`) вокруг найденной позы, но если refine уводит далеко от consensus, он отклоняется.

Для real-time режима multi-gate consensus не перебирает полный декартов product
IPPE-кандидатов. Вместо этого используется быстрый seed-based поиск: каждая
single-gate позиция пробуется как центр, для каждого гейта выбирается ближайший
кандидат, затем cluster уточняется вокруг медианы.

У `solve(...)` есть параметр `refine`. Если `refine=False`, solver возвращает
consensus pose без дорогого joint `SOLVEPNP_ITERATIVE`. Это используется в
real-time gate localization для 4+ видимых ворот.

Практический результат: multi-gate режим лучше стабилизирует **позицию XZ**, чем одиночный planar PnP. Y и yaw пока остаются менее надёжными из-за зеркальных IPPE-кандидатов и качества/синхронизации данных.

## Ограничения и качество ground truth

Валидационный `ground_truth` получен из симулятора и может быть не идеально синхронизирован с изображением: позиция/ориентация иногда отстаёт на 1-2 кадра. Поэтому строгие ошибки относительно GT нельзя всегда трактовать как ошибку solver-а.

При анализе качества нужно смотреть сразу на несколько признаков:

- `reprojection_rmse_px`
- согласованность поз между несколькими воротами
- выбранный consensus-кластер
- визуальную проверку overlay
- расхождение с GT как ориентир, но не абсолютную истину на уровне сантиметров/градусов

Текущий solver покрывает рабочие варианты порядка ключевых точек (`IDENT`, `HFLIP`). Остальные расхождения в multi-валидации в значительной степени связаны с planar-неоднозначностью, Y/yaw и возможным лагом телеметрии.

## Система координат и yaw

```
                  +Y (вверх)
                  |
    +Z (вглубь)---+--- +X (вправо)

yaw = 0° → камера смотрит вдоль +Z
yaw = 90° → камера смотрит вдоль +X
```

Yaw вычисляется из направления `cam_fwd_world` (третий столбец `R.T`):
```
yaw_deg = atan2(cam_fwd_world.x, cam_fwd_world.z) * 180 / pi
```

## Ожидаемая точность (ТЗ)

| Метрика | Цель |
|---|---|
| Позиция по X, Z | ≤ 0.2 м |
| Позиция по Y | ≤ 0.1 м |
| Yaw | ≤ 2° |
| Ошибка репроекции | < 3 px |

Для текущих calibration/multi данных эти пороги нужно использовать как **идеальную цель**. Из-за planar ambiguity и возможной задержки телеметрии более информативны также XZ-consensus, RMSE и визуальная проверка.
