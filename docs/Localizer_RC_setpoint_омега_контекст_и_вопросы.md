# Localizer для RC-only через setpoint ω: контекст и открытые вопросы

Дата: 2026-05-06

Файл-памятка для следующей рабочей сессии. Здесь собран весь контекст обсуждения,
выводы по текущему состоянию кода и список вопросов, на которые нужно ответить
до реализации.

---

## 1. Цель

Сделать так, чтобы Localizer работал **независимо от источника стиков**:

- режим Liftoff (UDP): как сейчас — поля `in_throttle/yaw/pitch/roll`;
- режим RC-only (UART/ESP32): по сырым каналам `ch1..ch8`;
- режим «оба»: оба источника эквивалентны.

Способ — привести стики из обоих источников к **единому домену** через
**Rate-профиль пилота** (`profiles/rates/*.json`). Каждый пилот указывает свой
Rate, и localizer должен быть инвариантен к выбору профиля.

В перспективе планируется писать в сессию ещё и сам **setpoint ω** как явное поле,
чтобы убрать неоднозначность «что считать целевым °/с».

---

## 2. Что уже есть в репозитории (важные факты из кода)

### 2.1 UDP-пакет Liftoff содержит **разделённые** поля
Файл: `dct/receivers/liftoff_udp.py`

- `gyro_pitch/roll/yaw` (float) — **фактическая** угловая скорость, **град/с**;
- `in_throttle/yaw/pitch/roll` (float) — **команда стиков**, обычно −1..1.

То есть DCT уже принимает **и факт, и команду**. Setpoint ω в записи **отсутствует** —
его восстановление из стиков и есть текущая задача.

### 2.2 RC по UART
Файл: `dct/rc_receiver.py`, контракт в `docs/DCT_Входы_и_выходы_контракт_данных.md`

- CSV: `<ts_us>,<ch1>,<ch2>,<ch3>,<ch4>,<ch5>,<ch6>,<ch7>,<ch8>`;
- `ch1..ch4` — стики в µs (~988..2012);
- `ch5..ch8` — тумблеры (см. README: `ch8` = Rate profile);
- частота — выше Liftoff'а, привязка времени через якорь + `micros()`.

Маппинг каналов (из `dct/gui/widgets/stick_graphs.py` и README):
`ch1=roll, ch2=pitch, ch3=throttle, ch4=yaw`.

### 2.3 Rate-профили на диске
Папка: `profiles/rates/*.json`

Формат:
```json
{
  "id": "rate_3",
  "model": "betaflight",
  "name": "Salie1_330_rate",
  "pitch": { "rc_rate": 1.02, "rate": 0.69, "expo": 0.00 },
  "roll":  { "rc_rate": 0.91, "rate": 0.65, "expo": 0.00 },
  "yaw":   { "rc_rate": 0.85, "rate": 0.65, "expo": 0.00 }
}
```

В коде DCT этот JSON **только сохраняется в `cfg["rate"]`** при старте записи
(`dct/gui/widgets/record_bar.py`, `_on_start`) и не применяется к стикам.
Никакого `betaflight rates` пересчёта в Python сейчас нет (`grep` по
`betaflight|rc_rate|deg_per` → пусто в `*.py`).

### 2.4 Текущий Localizer
Файл: `dct/localization/online_localizer.py`

Ключевая деталь — нормализация эталона **z-score** по построенному кругу:

```python
# Reference.build
sticks_sm = _smooth_box(sticks, smooth_w)
mean = sticks_sm.mean(axis=0)
std  = sticks_sm.std(axis=0) + 1e-6
sticks_norm = (sticks_sm - mean) / std
```

И на онлайне (`OnlineLocalizer.update`) то же самое:
```python
stick_norm = (smoothed - self.ref.mean) / self.ref.std
```

Следствия:
- общий **линейный масштаб** rate уже частично абсорбируется через `std`;
- **expo** и **super rate** через z-score не уходят (это нелинейности);
- эталон жёстко привязан к домену **`in_*` Liftoff**, в порядке
  `[throttle, yaw, pitch, roll]`, диапазон ~±1.

Источник стиков для сборки эталона — `lap_loader.py`, колонки
`STICK_COLS = ["input_throttle", "input_yaw", "input_pitch", "input_roll"]`,
т.е. эталоны строятся **исключительно из Liftoff-сессий**.

## 3. Математика: setpoint ω в Rate mode (Betaflight classic)

Это та модель, которая описана полями `rc_rate`, `rate`, `expo` в текущих JSON
(`"model": "betaflight"`).

Для каждой оси (roll/pitch/yaw) **независимо**:

1. **Нормализация в `s ∈ [-1, 1]`** — учёт центра, эндпоинтов, deadband, инверсии.
2. **Expo** — нелинейность около центра; типовая форма
   ```
   s_ex = s · (1 - ε) + s³ · ε,    ε = expo / 100
   ```
   На максимуме хода в этой форме знака не меняет, кривая «мягче» у нуля.
3. **Rates → setpoint, °/с** — структурно:
   ```
   ω_sp = s_ex · ( k_rc · rc_rate + k_sr · rate · |s_ex| )
   ```
   - первый член — базовая чувствительность (наклон у центра);
   - второй — super rate, добавляется к краям;
   - точные `k_rc`, `k_sr` и **что именно** идёт под `|·|` (s или s_ex,
     до или после expo) — зависит от **версии Betaflight/конфигуратора**;
     это известное расхождение (см. issue #7110 в betaflight/betaflight).
4. **Ограничения** — лимиты °/с по осям (yaw обычно отдельно).

Throttle:
- к нему **не применяется** ω-преобразование;
- вход `in_throttle` ~ 0..1 или −1..1 (контракт), для сравнения нужен отдельный
  выбор: оставить 0..1, либо вообще убрать из вектора локализации.

Альтернатива — **Actual Rates** (BF 4.3+): задают чувствительность в центре и
максимум °/с напрямую, формула другая. Текущие JSON эту модель **не описывают**.

## 4. Идея пользователя

> Перевести стики из симулятора и с RC в **единые значения** через Rate-профиль,
> заданный при записи. Каждый пилот → свой профиль. Localizer работает на этих
> «единых значениях» одинаково и на Liftoff, и на RC, и не зависит от пилота.

---

## 5. Аналитика идеи

### 5.1 Это две независимые задачи

**A. Унификация источников.**
Привести RC к тому же домену, что и Liftoff `in_*` (или оба — к третьему домену).
Без этого localizer на RC-only физически не запустится — у него уже есть эталон,
обученный на Liftoff.

**B. Инвариантность к Rate-профилю.**
Чтобы эталон одного пилота **переиспользовался** другим пилотом с другим Rate'ом,
сигнал должен быть инвариантен к Rate. Самый чистый кандидат — **setpoint ω в °/с**:
- физическая величина;
- проверяема по `gyro_*` Liftoff;
- по построению не зависит от Rate (после корректного применения формулы).

Альтернатива — «канонический стик» в [-1..1] через **обратное** применение
expo+rate: `s_canon = invRates(ω_sp_RC)`. Только унификация формы, без физики.

### 5.2 Эффект z-score normalization в localizer'е

Текущая `(s - mean)/std`:
- частично гасит **общий масштаб** Rate (разные `rc_rate` у пилотов);
- **не** гасит expo и super rate (это нелинейности);
- если перейдём в физический домен (°/с), z-score опять «съест» масштаб — стоит
  подумать о замене на нормализацию по **фиксированным** диапазонам
  (например, ±max_rate или фиксированные ±1000 °/с), чтобы сохранить
  сравнимость между пилотами.

### 5.3 Зависимости и риски

1. **Семантика `in_*` из Liftoff** — критическая неизвестная.
   Это сырой стик (после deadband/центровки) или уже после кривых самого
   симулятора? От ответа зависит вся цепочка.
2. **Совпадение Rate-профиля в Liftoff/FC и в JSON DCT** — если внутри Liftoff
   стоит другой Rate, чем выбран в DCT, восстановленный из `in_*` setpoint
   ≠ восстановленный из RC setpoint.
3. **Эталоны несовместимы между доменами** — все существующие
   `tracks/track-XXX/references/default.npz` нужно либо пересобрать в новом
   домене, либо ввести версионирование/`domain`-метку.
4. **Throttle не имеет ω** — отдельное решение.
5. **Калибровка RC TX** — реальные центр/эндпоинты/deadband отличаются от
   номинальных 988/1500/2012 µs (триммы, ELRS). Без калибровки разные TX дадут
   разный ω при одинаковом физическом действии.
6. **Частоты** — Liftoff ~100 Hz, RC обычно ~50–250 Hz; для localizer'а нужен
   общий темп, придётся ресемплировать/выравнивать по `ts_wall`.
7. **Версия rates model** — JSON говорит `"betaflight"`, но это classic.
   Реальные FC/Liftoff могут быть на Actual Rates (BF 4.3+).
8. **Порядок осей и знаки** — localizer ждёт `[throttle, yaw, pitch, roll]`,
   RC: `ch1=roll, ch2=pitch, ch3=throttle, ch4=yaw`. Любая ошибка инверсии
   → правдоподобный, но неверный ω.

## 6. Открытые вопросы (требуют ответа до реализации)

1. **Что Liftoff кладёт в `in_*`?**
   - сырой стик (до Rate),
   - или уже команда после кривых симулятора (фактически setpoint в его
     внутренних единицах)?
   План проверки: записать пару секунд при разных настройках Rate в Liftoff
   и сравнить диапазоны/форму `in_*` при том же физическом дефлексе.

2. **Где «истинный» Rate-профиль?**
   В Liftoff/эмуляции FC и в DCT JSON во время записи стоит **один и тот же**
   Rate? Если нет — какой из них считать каноническим для setpoint?

3. **Целевой общий домен localizer'а:**
   - (a) `setpoint ω` °/с по 3 осям (без throttle), вектор 3D;
   - (b) `setpoint ω` °/с + throttle отдельным каналом, 4D;
   - (c) «канонический стик» в [-1..1] через inverse expo+rate, 4D;
   - (d) минимально: просто унифицированный нормализованный стик [-1..1] без
     учёта Rate (Liftoff `in_*` ↔ RC PWM → −1..1).

4. **Throttle:**
   оставить в векторе локализации или убрать?

5. **Эталоны:**
   - пересобрать все `default.npz` в новом домене и считать старые невалидными;
   - или ввести версионирование (`domain` в `meta.json` рядом с npz),
     поддержав оба варианта параллельно.

6. **Где делать конвертацию:**
   - в `data_source` (live) — единый поток для GUI, parquet и localizer'а;
   - или внутри localizer'а — GUI и parquet остаются как сейчас.
   Решение влияет на схему `telemetry.parquet`/`rc_channels.parquet` — нужно ли
   добавлять колонки `omega_sp_pitch/roll/yaw`.

7. **Калибровка RC TX:**
   хранить per-pilot/per-tx (центр, мин/макс, deadband для каждого канала)
   рядом с Rate-профилем, или считать достаточным номинал 988/1500/2012 µs
   и общий deadband?

8. **Rate model:**
   только classic Betaflight (как сейчас в JSON), или поддержать ещё Actual
   Rates? В JSON стоит явно хранить версию формулы (`"model"` уже есть, но не
   проверяется в коде).

9. **Кросс-валидация:**
   будет ли использоваться режим «оба источника» одной сессии для проверки,
   что setpoint, восстановленный из RC, совпадает с восстановленным из `in_*`
   Liftoff? Это естественный тест корректности перед переходом на RC-only.

   и/или rc_channels), как явный setpoint в записи.
