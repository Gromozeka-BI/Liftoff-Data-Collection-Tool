# ТЗ для системы визуальной локализации (камерный модуль)

Документ — формальный выход Эксперимента 10. Описывает требования к будущему
камерному подмодулю, который будет периодически выдавать абсолютные XYZ-
координаты дрона на трассе.

## 1. Контекст

Текущий локализатор использует только данные стиков (RC + Rate-profile + PF) и
достигает следующих p90-ошибок на track-002 (Abu-Dhabi, ~314 м):

| Условие              | Тестовая сессия | mean p90 (без камеры) |
|----------------------|-----------------|------------------------|
| Same-drone (hold-out) | MT_s004 (15 лапов)  | **12.36 м** |
| Cross-drone           | LO_s001 (6 лапов)   | **6.49 м**  |

Камерный модуль должен дополнить локализатор: периодически (период `T_update`)
сообщать XYZ-наблюдение позиции дрона в системе координат трассы с известной
изотропной неопределённостью `σ_cam` (м). Слияние реализовано как 3D
Bayes-update частиц фильтра — см. `OnlineLocalizer.inject_position_observation`.

## 2. Требования к точности и частоте

Требования заданы в виде **Pareto-фронта** (σ_cam, T_update) — допустимы любые
комбинации, попадающие в указанные «коробки». Все цифры — mean p90 по 5 seeds.

### 2.1 Same-drone (доминирующий сценарий)

**Базовая линия**: 12.36 м.

| Уровень | σ_cam, м | T_update, с (частота, Гц) | Ожидаемый p90, м | Δ, % |
|---|---|---|---|---|
| **Минимально полезный** (Δ ≥ 20%)  | ≤ 10 | ≤ 1.0 (≥ 1 Гц)  | 9.5  | −23% |
| **Хороший** (Δ ≥ 40%)             | ≤ 5  | ≤ 1.0 (≥ 1 Гц)  | 6.0  | −51% |
|                                   | ≤ 10 | ≤ 0.5 (≥ 2 Гц)  | 6.9  | −44% |
| **Целевой** (Δ ≥ 60%)             | ≤ 3  | ≤ 0.5 (≥ 2 Гц)  | 4.6  | −63% |
|                                   | ≤ 5  | ≤ 0.2 (≥ 5 Гц)  | 4.5  | −64% |
|                                   | ≤ 1  | ≤ 1.0 (≥ 1 Гц)  | 4.6  | −63% |
| **Идеальный**                     | ≤ 1  | ≤ 0.2 (≥ 5 Гц)  | **2.5**  | **−80%** |

### 2.2 Cross-drone (нижняя граница «лёгкого» сценария)

**Базовая линия**: 6.49 м (уже хорошо, выигрыш меньше в относительных %).

| Уровень | σ_cam, м | T_update, с (частота, Гц) | Ожидаемый p90, м | Δ, % |
|---|---|---|---|---|
| **Минимально полезный** (Δ ≥ 20%)  | ≤ 5  | ≤ 0.5 (≥ 2 Гц)  | 4.8  | −26% |
|                                   | ≤ 3  | ≤ 1.0 (≥ 1 Гц)  | 4.8  | −25% |
| **Хороший** (Δ ≥ 40%)             | ≤ 3  | ≤ 0.2 (≥ 5 Гц)  | 3.4  | −47% |
| **Целевой** (Δ ≥ 60%)             | ≤ 1  | ≤ 0.5 (≥ 2 Гц)  | 2.9  | −55% |
| **Идеальный**                     | ≤ 1  | ≤ 0.2 (≥ 5 Гц)  | **1.9**  | **−70%** |

### 2.3 Запрещённые режимы

**σ_cam ≥ 10 м с T_update > 1 с** на cross-drone делает p90 **в 1.5 раза хуже
базовой линии** (например, σ=20м, T=1с → p90=10.1 м vs baseline 6.5 м).

Объяснение: одно «плохое» (≫σ_obs стиков) наблюдение «обнуляет» накопленную
информацию из стиков — Bayes-веса перерасходуются на широкое 3D-распределение.

**Рекомендация**: если камерный модуль не уверен в точности (`σ_cam ≥ 10 м`)
или редко обновляется (`T_update ≥ 5 с`), его лучше **отключать**, а не
подмешивать в фильтр.

## 3. Технический интерфейс

```python
from dct.localization.online_localizer import OnlineLocalizer

loc = OnlineLocalizer.from_file("track-002/reference.npz")
loc.reset()

# В горячем цикле:
result = loc.update(sticks_4ch, dt, rate_profile=current_rate_profile)

# Когда камера выдаёт наблюдение:
result = loc.inject_position_observation(
    xyz_obs=(x_m, y_m, z_m),  # м, в системе координат трассы
    sigma_cam=σ_cam_m,         # СКО (изотропно), м
)
```

Метод реализован в `dct.localization.online_localizer.OnlineLocalizer`.
Вызовы можно делать асинхронно с `update()`; они корректно встраиваются в
байесову цепочку (3D-likelihood частицы + ESS-чек + systematic resampling).

## 4. Требования к камерному модулю

| # | Параметр | Минимум | Цель | Идеал |
|---|---|---|---|---|
| 1 | Частота обновлений    | ≥ 1 Гц    | ≥ 2 Гц     | ≥ 5 Гц     |
| 2 | σ_cam (СКО), м         | ≤ 5       | ≤ 3        | ≤ 1        |
| 3 | Латентность, мс        | ≤ 1000    | ≤ 500      | ≤ 200      |
| 4 | Система координат      | согласована с `track.json` (gates) |
| 5 | Калибровка σ_cam       | модуль должен сам оценивать `σ_cam` (например, residual reprojection в PnP); недопустимо «занижение» — фильтр накажет |

При выполнении «целевого» уровня (σ_cam ≤ 3м @ ≥ 2 Гц) ожидается общий
p90 локализатора ≤ 4 м на любой стандартной сессии track-002.

## 5. Замечания

- Все требования получены на track-002 с дефолтными PF-параметрами Exp 3
  (σ_obs = 2.0, pnv = 8.0, weights = no_thr).
- На «свежих» трассах (Exp 8: track-003, track-004) дефолтный σ_obs не
  оптимален — там нужно σ_obs ≈ 4. После настройки σ_obs камерная фьюжн
  ожидаемо даст похожий или лучший выигрыш (та же физика).
- Шум симулировался как изотропный (σ_x = σ_y = σ_z). Реальные камеры могут
  иметь анизотропную точность (хуже по глубине). При необходимости интерфейс
  расширяется до диагональной/полной ковариации (одна строка в
  `inject_position_observation_xyz`).
- Камеру с σ_cam > 10 м рекомендуется **не подмешивать**, а отключать —
  иначе она ухудшает уже достигнутую стиками точность.
