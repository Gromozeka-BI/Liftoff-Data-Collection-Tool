# Эксперимент 5: Кросс-пилотная обобщаемость

## Исследовательский вопрос
Может ли локализатор, построенный на основе референса пилота A, точно отслеживать
полёт другого пилота на той же трассе?

Является ли стиль пилота значимым фактором по сравнению с типом дрона (Exp 1, η²=0.41)?

---

## Ключевые выводы

### 1. Стиль пилота — доминирующий фактор (сильнее типа дрона)
Среднее кросс-пилот p90 (66–105 м) значительно превышает кросс-дроновый результат из Exp 4 (9.7 м).
Признаки угловых скоростей более специфичны для конкретного пилота, чем для конкретного дрона.

### 2. Пресет `angular_scaled` значительно улучшает кросс-пилотное отслеживание
- Тот же пилот: все пресеты сопоставимы (11–12 м)
- Другой пилот: `angular_scaled` → 66 м против `no_thr` → 97 м — **улучшение на 32%**
- Веса angular_scaled (thr=0, yaw=0.7, pitch=0.5, roll=1.0) акцентируют крен и подавляют
  тангаж/рысканье, которые наиболее сильно зависят от стиля пилота.

### 3. Сильная асимметрия обобщения: GromFF_1 — универсальный референс
GromFF_1 (Gromozeka) показывает замечательное кросс-пилотное отслеживание для PlatOnAir:
- GromFF_1 → PlatOnAir: p90 = **17.7 м** (angular_scaled) — близко к целевому порогу 15 м!
- GromFF_1 → RedSeep: p90 = 104 м — неудовлетворительно (PlatOnAir и Gromozeka летают схожим образом)
Качество и «универсальность» GromFF_1 (равномерные круги, подтверждено в Exp 4)
делают его наиболее обобщаемым из всех наблюдавшихся референсов.

### 4. Внутрисессионное отслеживание (тот же пилот) — отличное
PlatOnAir_1 → тест PlatOnAir (та же сессия, разные круги): p90 = **6.5 м** (no_thr).
Это сопоставимо с потолком same-drone из Exp 4 (5.8 м), что подтверждает:
система работает отлично, когда референсная и тестовая сессии совпадают по скорости и траектории.

### 5. Скорость и пространственная траектория должны совпадать
Когда референсная и тестовая сессии имеют разное время круга (например, RedSeep session-001
при 21 с/круг против session-002 при 17–18 с/круг), фильтр полностью расходится даже для
одного пилота. Пространственная траектория меняется вместе со скоростью полёта, что приводит
к несоответствию признаков.

## Системные баги, обнаруженные в ходе эксперимента

### Баг 1: Отсутствие `invert_lf` при программном построении референса
**Проблема**: функция `reference_builder.build()` требует явной передачи словаря `invert_lf`
(из файла `invert.json` сессии) для корректной обработки знака канала крена (roll).
При построении референсов из скриптов (не через GUI) пропуск этого параметра приводит
к тому, что признаки крена оказываются **перевёрнутыми**, и референс становится несовместим
с любыми тестовыми данными.

**Симптом**: фильтр выдаёт полностью случайные оценки (p90 ≈ L/2), корреляция признака
крена между референсом и тестом = −1.0 вместо +1.0.

**Исправление**: всегда передавать
`invert_lf = json.loads((session/"invert.json").read_text())["lf"]`
в `reference_builder.build()`.

### Баг 2: `v_init` должен вычисляться из скорости пилота
**Проблема**: дефолтное значение `v_init_mps=10.0` откалибровано под скорость Gromozeka
(~13 м/с). Более быстрые пилоты (17–18 м/с) приводят к тому, что все частицы отстают
от дрона, и фильтр окончательно расходится.

**Исправление**: вычислять `v_init = ref.L / (ref.sticks_norm.shape[0] / 100.0)`
из данных референса.

Оба бага **исправлены в скрипте эксперимента** и задокументированы для основного API
`OnlineLocalizer` и всех будущих скриптов построения референсов.
